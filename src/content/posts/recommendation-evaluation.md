一张结果表能说明多少问题，取决于表格之外记录了多少实验条件。这篇示例整理一份可以复用的评估记录清单。

## 把实验条件放在模型之前

准备实验时，可以先写下数据的时间范围、用户和物品的过滤规则、训练集与测试集的构造方式。明确这些条件，之后的模型比较才有共同的起点。

尤其需要检查：用于训练的输入和特征，是否包含了评估时本不应提前知道的信息。

## 候选集合也是协议的一部分

评估时使用全部可用物品，还是采样一部分候选物品？是否过滤用户已经交互过的物品？这类设置需要与指标一起记录。

| 项目     | 建议记录                       |
| -------- | ------------------------------ |
| 数据切分 | 按时间或其他规则切分的具体方式 |
| 候选物品 | 全量候选或采样候选的定义       |
| 指标     | 指标名称、截断位置与实现       |
| 随机性   | 随机种子与重复次数             |
| 运行环境 | 代码版本、依赖与硬件           |

## 留一份能够复跑的记录

不妨让每次实验的目录保持一致。下面是目录组织示例，不对应任何实验结果。

```text
runs/
  baseline-001/
    config.yaml
    metrics.json
    notes.md
    environment.txt
```

在 notes.md 中，除了记录结果，还可以写下这次只改变了什么，以及观察到哪些无法解释的现象。

## 先建立可信的基线

第一轮可以从一个容易理解、容易复现的基线开始，再逐项改变模型或配置。每一次比较都保留相同的数据与评估设置，能减少解释结果时的歧义。

延伸阅读：[RecBole 官方项目](https://github.com/RUCAIBox/RecBole)。实际使用框架时，请以对应版本的配置和文档为准。
